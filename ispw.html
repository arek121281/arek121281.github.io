🔍 Czym jest ISPW?

Zarządzanie kodem źródłowym i release management na mainframe

📋 Definicja

ISPW (dawniej Compuware ISPW, obecnie BMC AMI DevX Source Code Management) to narzędzie do zarządzania kodem źródłowym (SCM), build i deploy na platformie mainframe z/OS. Jest odpowiednikiem Git + Jenkins + Release Manager, ale dla świata mainframe.

💡 Analogia

Jeśli Git zarządza kodem w świecie distributed, a Jenkins automatyzuje build i deploy, to ISPW robi to samo na mainframe — ale w jednym zintegrowanym pakiecie, ściśle powiązanym z cyklem życia komponentów COBOL, PL/I, Assembler i innych.

⚙️ Konfigurowalność lifecycle

ISPW pozwala definiować niestandardowe lifecycle per aplikacja:

  • Różna liczba poziomów (2-7+)
  • Bramki jakości (quality gates) między poziomami
  • Wymagane zatwierdzenia (approvals) przed promote
  • Automatyczny generate na promote
  • Webhook/event na każdą akcję (CI/CD trigger)
  • Oddzielne lifecycle dla emergency fixes (hotfix path)

🔥 Emergency Fix Path

Dla krytycznych poprawek produkcyjnych ISPW oferuje skrócony lifecycle: DEV → PRD (z pominięciem QA/STG), z pełnym audytem i opcjonalnym zatwierdzeniem.

⬇️ DEMOTE

Cofnięcie na niższy level (np. QA→DEV). Używane gdy testy wykazały błędy. Komponent wraca do dewelopera do poprawy.

🔙 REGRESS

Wycofanie z produkcji — przywraca poprzednią wersję load module'u. Krytyczna operacja z pełnym audytem.

🏗️ Generate & Deploy — szczegóły

Jak ISPW automatyzuje budowanie i wdrażanie

🔧 Build Process — pod maską

// ISPW Generate uruchamia JCL automatycznie: // 1. Dla programu COBOL z DB2: STEP 1: DB2 Precompile (DSNHPC) → wyodrębnia SQL, tworzy DBRM STEP 2: COBOL Compile (IGYCRCTL) → generuje object module → opcje: RENT, OPT(1), MAP, XREF STEP 3: Link-Edit (IEWL) → tworzy load module w docelowej LOADLIB STEP 4: DB2 BIND PLAN / PACKAGE → wiąże DBRM z planem DB2 // ISPW automatycznie: • Wybiera odpowiedni JCL skeleton per typ • Ustawia biblioteki per level (DEV/QA/STG/PRD) • Zachowuje listing kompilacji • Raportuje Return Code • RC 0-4: SUCCESS • RC 8+: FAILURE (task zatrzymany)

🚀 Deploy Process

Deploy w ISPW to kontrolowane przeniesienie na produkcję:

  1. Pre-deploy validation — czy wszystkie taski w assignment mają status GENERATED?
  2. Impact analysis — co jest zmieniane? Jakie programy są dotknięte?
  3. Approval workflow — zatwierdzenie przez Change Management, Release Manager
  4. Backup — automatyczna kopia aktualnych load modules (do regress)
  5. Deployment — kopiowanie nowych load modules do PROD LOADLIB
  6. DB2 BIND — bind nowych DBRM (jeśli zmieniony SQL)
  7. CICS NEWCOPY — odświeżenie programu w regionie CICS (jeśli online)
  8. Verification — smoke test, monitoring
  9. Close — zamknięcie assignmentu, aktualizacja ticketów

✅ Best Practices

Sprawdzone praktyki pracy z ISPW

✅ DO — rób tak

  • Zawsze twórz Assignment powiązany z ticketem (Jira/ServiceNow)
  • Generuj natychmiast po edycji — wyłapuj błędy kompilacji wcześnie
  • Używaj Impact Analysis przed promote — sprawdź zależności
  • Atomowe zmiany — jeden Assignment = jedna funkcjonalność
  • Testuj na QA zanim promujesz dalej
  • Włącz Git sync — backup i audyt w Git
  • Używaj Quality Gates — SonarQube + Total Test w pipeline
  • Dokumentuj — komentarz przy checkout i promote

❌ DON'T — unikaj

  • Nie edytuj na QA/STG — zawsze wracaj do DEV
  • Nie obchodź lifecycle — nie promuj bez testów
  • Nie zostawiaj locków — rób checkout tylko gdy faktycznie edytujesz
  • Nie ignoruj RC — return code > 4 = problem do rozwiązania
  • Nie mieszaj assignmentów — nie łącz niezwiązanych zmian
  • Nie deployuj w piątek — chyba że musisz (emergency)
  • Nie pomijaj regress planu — zawsze miej plan rollbacku
  • Nie modyfikuj PROD bezpośrednio — tylko przez ISPW

❓ FAQ — Najczęściej zadawane pytania

Jak cofnąć checkout (zwolnić lock) bez zapisywania zmian?▼
Użyj operacji UNDO CHECKOUT (lub Fallback). Przywraca komponent do stanu sprzed checkout, zwalnia lock i usuwa Task z Assignment. W Topaz: Right-click → ISPW → Undo Checkout. W ISPF: opcja U przy taskach.
Co jeśli Generate się nie powiedzie (RC > 4)?▼
Task pozostaje na danym poziomie ze statusem FAILED GENERATE. Nie można go promować. Sprawdź listing kompilacji (SYSPRINT) w ISPW — pokaże dokładne błędy COBOL/link-edit. Popraw kod i ponów Generate. Jeśli problem jest z copybookiem lub zależnością, użyj Impact Analysis.
Jak działa Impact Analysis?▼
Impact Analysis skanuje zależności: jeśli zmienisz copybook EMPREC, ISPW znajdzie wszystkie programy, które go COPY — i pokaże, które trzeba przekompilować. Można uruchomić IA manualnie lub ISPW automatycznie wyzwoli re-generate zależnych komponentów przy promote.
Czym różni się Assignment od Release?▼
Assignment — mały kontener (1 feature/bug fix), zwykle 1-10 tasków. Może być promowany niezależnie.
Release — duży kontener grupujący wiele Assignmentów. Wszystkie Assignmenty w Release muszą przejść lifecycle razem. Release zapewnia koordynację dużych wdrożeń (np. kwartalny release).
Jak ISPW współpracuje z Git?▼
ISPW-Git sync umożliwia dwukierunkową synchronizację: każda operacja w ISPW (checkout, generate, promote) jest odzwierciedlona jako commit w Git. Developerzy mogą też pracować lokalnie w IDE z Git i pushować do ISPW. To daje najlepsze z dwóch światów: mainframe lifecycle + Git history/branching.
Czym jest Runtime Configuration?▼
Runtime Configuration definiuje środowisko wykonania: jakie biblioteki (LOADLIB, COPYLIB, DBRMLIB) używa każdy level, jakie opcje kompilatora, jakie parametry DB2 BIND. Każda aplikacja może mieć różne runtime configs — np. oddzielne dla DEV i QA z różnymi bazami DB2.
